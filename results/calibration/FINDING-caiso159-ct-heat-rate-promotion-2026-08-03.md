## 1. Stop-the-line: a keeper bundle was corrupt on main

A rename/rename merge between the nyiso-113 and caiso-158 branches was
resolved by committing the **conflicted content into both paths**. Eight JSON
files across three bundles carried live `<<<<<<<<` / `========` / `>>>>>>>>`
markers on `main`, including `nyiso113_lilocational_B` — the **designated
NYISO keeper**.

The markers were the visible half. The damaging half was silent: git
**auto-merged the non-conflicting regions from the wrong side**, so the
keeper's committed scorecard asserted

| field | committed (corrupt) | truth |
|---|---|---|
| `criteria.governance.status` | `UNATTESTED` | `PASS` |
| `grade_summary.scored` | 8 | 9 |
| `grade_summary.target_grade` | 7 | 8 |

Those lines sit **outside every conflict marker**. A marker scan would have
declared the file clean after stripping, which is why the repair restores
whole blobs from the last-good commit (`81d61f1`) rather than editing markers
out. `nyiso_c156_meter_screen_B` had no clean blob anywhere — its pre-rebase
commit `794e42f` is unreachable — so it was reconstructed by selecting the
theirs-side of every hunk, which is lossless because a two-sided conflict
interleaves only the differing hunks.

**Blast radius, measured not assumed.** The corruption was confined to the
committed bundle JSONs. `frontend/data/backcast/runs/<id>.js` embeds no
scorecard (0 occurrences of `UNATTESTED`, no `governance` or `target_grade`
keys), and `status/NYISO.js` is regenerated by re-running the scorer against
the bundle's *attestation*, which was intact — so the dashboard never
displayed a wrong number. Nothing had to be re-solved.

**Transferable lesson.** `git merge` resolving a rename/rename conflict on a
pair of near-identical generated JSON files will interleave hunks *and*
silently splice the non-conflicting remainder. For bundle artifacts, never
hand-resolve: restore each side's blob whole.

## 2. The promotion premise had expired for one ISO

The caiso-158 handoff listed three promotable ISOs. Re-diffing each arm's
`ScenarioConfig` against the **current** designated keeper — not the keeper
that was current when the arms were chartered — gives:

| ISO | arm B vs CURRENT keeper | verdict |
|---|---|---|
| CAISO | **0** field diffs vs `caiso157_restore_B` | promotable |
| NEISO | 7 diffs, all schema drift | promotable |
| NYISO | **1 real diff**: `nyiso_li_locational_reserve` keeper=`True` arm=`False` | **NOT promotable** |

NEISO's seven (`caiso_firm_import_selfsched_clip`, `coal_prb_committed_split`,
`crossover_solve_year_weather`, `ercot_dam_availability_gas_event_cap`,
`gas_offer_margin_zonal_anchor`, `miso_coal_night_floor`,
`pjm_rggi_allowance_pricing`) were each ADDED to `ScenarioConfig` after the
neiso-72 solve, each defaults to `False`, and the arm records every one as
`False` — the incumbent simply predates the field. Schema drift, zero
behavioural delta.

NYISO's one is real. The keeper moved to nyiso-113 on 2026-08-02, which arms
the **published NYISO Long Island (Zone K) locational reserve ladder**. The
caiso-158 NYISO arms were controlled against nyiso-112, with that field off.
Promoting arm B would have traded a published requirement for an input
correction — a rule 14 `[R-ACCURATE]` regression in the name of rule 14. It is
filed for a re-solve, not absorbed.

**This is the session's most transferable procedural finding:** an A/B is only
promotable against the keeper it was controlled on. Re-diff at **promotion
time**, because a parallel per-ISO session can promote underneath you while
your arms solve.

## 3. What was actually blocking CAISO and NEISO

Nothing evidentiary. Both arms already reproduced their incumbent on every
model-determined criterion; the only differences were attestation-dependent
bookkeeping. A probe bundle carries no rule-21 DOF ledger, so C6 scored
`UNATTESTED` and `_apply_ledger` could not downgrade the ledgered
`FAIL → CAVEAT`, which dragged the determination to `NOT-YET`.

`scripts/gen_caiso159_attestation.py` carries each incumbent's attestation
forward with:

* a rewritten `governance.attested_by` describing the meter screen,
* every ledgered exception's `magnitude` **re-measured from the arm's own
  committed sidecars**,
* a new `ct_heat_rate_artifact` block pinning the artifact's path, md5,
  cap-weighted applied rate and plant coverage, and
* the DOF ledger carried **verbatim**, with the script **raising** if
  `n_entries` or `n_residual` moves — an input correction that changes the
  ledger is a contradiction, so it fails loudly rather than being trusted.

Nothing in it is hand-typed from a solve. (The md5s were briefly hardcoded
while drafting and were **wrong in their tails**; they are now computed at run
time. A hash quoted from memory into a keeper note is a fabricated provenance
claim.)
