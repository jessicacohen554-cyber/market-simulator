## 2. API re-discovery (task 0) — the working form

Read from the portal's own bundle, `https://portal.spp.org/static/js/main.e2bac944.js`
(the hash changes between deploys; re-read it rather than trusting this document).
`portal.spp.org` is a React SPA and the bundle is the authoritative definition.

```
listing   GET /file-browser-api/?fsName=<fs>&path=<p>&type=folder
download  GET /file-browser-api/download/<fs>?path=<p>
headers   X-SPP-UI-Token: <token>   Accept: application/json   Content-Type: application/json
```

Details that matter and were verified by probe, not assumed:

- `path` is sent through `URLSearchParams`, so `/` arrives percent-encoded. The SPA's **first**
  call is `path=""` (`componentDidMount(){ this.getFiles("") }`); folder rows carry their own
  `path` for navigation.
- The **trailing slash on `file-browser-api/` is part of the route** — dropping it returns 404.
  Omitting `type` also returns 404. Both 404s prove the router is reachable and discriminating.
- `fsName` is the page's `pcValue`, readable at `GET /api/pageConfig/by-slug/<slug>`. For every
  product above it equals the slug — so **the builder's `FS_DA` / `FS_RT` constants were right
  all along**.

**Why `[]` is an authorization result and not a wrong key** — the discriminating probe:

| Probe | Result |
|---|---|
| `fsName=rtbm-lmp-by-location` (real) | **200** `[]` |
| `fsName=zzz-not-a-real-source` (invented) | **404** |

A bad key 404s. A good key 200s with nothing in it. Supporting evidence: `/api/principal`
returns `unauthenticatedUser: true, uiTokenPresent: false`; every response carries SPP's own
`JSESSIONID` + Spring-Security headers, so it is **SPP's Tomcat answering, not our egress
proxy** (separately confirmed against the proxy's own failure log, which records no `curl`
failure for `portal.spp.org` at all).

Ruled out, each by probe: a `curl` User-Agent filter (a full Chrome header set with `Referer`,
`Origin` and `Sec-Fetch-*` returns the same `[]`); a missing session (`JSESSIONID` + `XSRF-TOKEN`
established through the page flow, same `[]`); a path-encoding change (**40 combinations** of
`type` × `path` — encoded, raw, empty, leading-slash, trailing-slash, `.`, glob — all `[]`);
and a different host (`marketplace.spp.org` just redirects).

This is a change since the builder last ran: `actual_lmp_hourly_SPP.parquet` is committed,
complete (8,760 × 3 years, 2023–2025, means $23.47 / $23.31 / $27.11 RT) and landed
**2026-09-05** — one day before this probe. Plan §2.4's independent probe the same day agrees.
The working form is recorded in the builder's module docstring with the date, as the charter
requires.

**The unblocked route nobody has tried.** SPP's *System Interfaces Stakeholder Reference Guide*
(now tracked at `data/raw/spp-planning/`) states under **Programmatic Interfaces**: *"SPP also
supports the use of TCP/IP for interfacing with AGC, ICCP, and PMU as well as **FTP for the
programmatic retrieval of Public Data**."* Its Public Data Specifications section names a
dedicated **"SPP Public Data Access"** guide — *"Reference guide for accessing public data via
the SPP Portal **and FTP**"* — under Stakeholder Center > User Guides, APIs & Integrations >
Technical Reference Documents > Public Data. **That FTP route is the highest-value next probe
for rows 5–9** and may not need the UI token at all. This lane did not pursue it: the charter's
stop rule fires on a login requirement, and chasing an untried transport past that point risked
spending the session on it instead of rows 10–13.

## 3. `--per-hub` and the byte-identity proof (task 1)

`scripts/data/build_spp_lmp_reference.py` (332 → 485 lines) gains `--per-hub`, which emits
`year`/`hour`/`zone`/`rt`/`da` (one row per hub per hour) to
`actual_lmp_hourly_zonal_SPP.parquet`, on the same fixed non-leap 8760 local calendar as
`derive_actual_lmp.py`. Rule 27 `[R-PUSH]`: edited with the Edit tool, exact on-disk bytes
pushed, blob verified after push (§9).

Shape of the change: the read/filter/concat step became `_monthly_frame()` and the
day→hour-of-year mapping became `_dense_from_daily()`; `_parse_monthly()` now calls both and
is otherwise the identical sequence of statements. `_parse_monthly_by_hub()` is new and differs
in exactly one line — it groups within one hub instead of across both.

**`zone` carries the SPP settlement-location name (`SPPNORTH_HUB` / `SPPSOUTH_HUB`), not a
model zone name.** SPP has no registered topology; naming zones here would pre-empt card P1.
SPP-20/SPP-31 re-key it. (MISO's sibling file has both a `hub` and a `zone` column; SPP gets
one, per this lane's charter, until there are model zones to put in the second.)

### The proof the default output cannot move

The portal is blocked, so byte-identity could not be shown by re-running the builder against
live data. It was shown **network-independently instead**, by running `HEAD`'s builder and the
post-change builder over the same synthetic fixture — 12 monthly wide CSVs per year, both hubs,
scattered NaNs (including cells where one hub is missing and cells where both are), both of
SPP's `Date` formats, a non-LMP row that must be filtered, a leap-year Feb 29, and a next-year
December spillover row that must be dropped:

| Proof | Result |
|---|---|
| 1 · `_parse_monthly` HEAD vs post-change, 2023 / 2024 / 2025 / 2028 | **identical** (`np.array_equal(..., equal_nan=True)`) in all four |
| 2 · **emitted parquet sha256**, 3-year default build | `0ab1c195…c116dbb9` both sides — **byte-identical**, 26,280 rows |
| 3 · system series == NaN-skipping mean of the two per-hub series | exact, incl. the 65–71 hours/yr where **both** hubs are NaN |
| 4 · `--per-hub` frame | 17,520 rows = 8760 × 2, dtypes `int16/int16/str/float32/float32`, zones as expected |

Proof 2 is the load-bearing one: the default `--out` parquet is byte-identical, not merely
numerically equal. Proof 3 is what makes `--per-hub` and the default two views of one parse
rather than two parsers that could drift.

**`--per-hub` has never been run against live SPP data** and cannot be until the portal
unblocks. It is implemented and fixture-tested, nothing more; the docstring says so.

A permanent guard test belongs in `tests/`, which is **outside this lane's file ownership** —
flagged for whoever owns it. The proof script is not committed (it is a throwaway diagnostic);
this section is the record, per rule 15's git-history-is-the-record discipline.

### Addendum (C) — the one line the desk asked for

> **The desk's 2024 screen-year ruling STANDS, and nothing in this lane overrides it.** The
> +$12 the desk ruled on is confirmed verbatim from ASOM 2025 Figure 4-7 (p. 122: North $28,
> South $40), and 2024 is *also* the widest year on the independent all-hours measure
> (~$9/MWh, against ~$2–3 in 2023 and ~$1 in 2025) — so both published measures rank 2024
> first among the training years. **The hourly mean and p90 of |SPPNORTH − SPPSOUTH| could
> not be computed** (portal blocked), so the number that would have been able to disagree
> does not exist; the ruling is confirmed on published evidence, not merely unchallenged.

Within 2023–2025 the ordering is **2024 (~$9) ≫ 2023 (~$2–3) > 2025 (~$1)** — and note that
2024 is the widest by a factor of three-to-nine, not a marginal win. That margin is what makes
the screen-year choice robust to the difference between the published annual mean and the
hourly mean it stands in for.

**What is still owed and cannot be faked:** `mean` and `p90` of the hourly `|N − S|`. The p90
in particular is not recoverable from an annual mean — the whole point of a p90 is the tail,
and the MMU's own figures show that tail is large (October 2024 alone reached a **~$33/MWh**
monthly spread, "the largest monthly spread … since the start of the Integrated Marketplace").
Run `--per-hub` and compute both the moment the portal unblocks.

### Direction and diurnal shape — structural evidence for the N↔S link

Not asked for, but it is the measured signature the model's N↔S link has to reproduce, and it
came free with the spread:

- **Sign:** South is normally dearer — *"Coal, nuclear, and wind are the dominant fuels in the
  north and west. The south and east have a much larger share of gas generation"* (all three
  editions). But the sign **reverses for part of every recent year**, and increasingly:
  a few months in 2023; February and March 2024; and in 2025 **six months DA / eight months
  RT**, which the MMU attributes to *"congestion around North hub settlement locations"*.
  A model that can only ever price South above North will miss most of 2025.
- **Diurnal (2024, ASOM 2024 p. 120):** the hubs sit within **~$5/MWh for HE1–HE11 and the last
  three hours**, diverge from **HE12**, and peak at **~$25/MWh at HE16/17/18**. The MMU's
  stated driver — *"higher priced gas generation in the south"* — is a merit-order effect, and
  it is a sharper structural target for card P7's STOP gate ("link binds in the measured
  direction/season") than any annual mean.

## 6. What landed from `www.spp.org` (tasks 3–4) — including two corrections

Full transcriptions with page cites in `data/raw/spp-planning/README.md`. Two of these
**contradict assumptions the plan is currently carrying**, which is the main reason to read

### ⚠️ Correction 1 — PRM is 16 %, not 15 %, and there is no single system-wide PRM

`SPP Planning Criteria v5.0A` §4, printed p. 10. Plan §6 row 12 records *"PRM (15 % since
PY2023; winter PRM from 2026)"*. The live criteria say:

| BAA | Summer | Winter |
|---|---|---|
| **East** | **16 %** (2026, 2027, 2028) → **17 %** (2029) | **36 %** (2026/27, 2027/28, 2028/29) → **38 %** (2029/30) |
| **West** | **19 %** (2027) | **40 %** (2027/28) |

The winter half of the plan's note is right in kind; **the 15 % is not the live number**. Two
things follow for SPP-20: SPP East and SPP West carry **separate** Base PRMs set by separate
LOLE studies, so whatever zones card P1 registers must be mapped to a **BAA** before a PRM is
applied — SPP has no one system-wide PRM. The RTO footprint this program models is the **East**
BAA.

### ⚠️ Correction 2 — SPP's energy offer cap is $1,000/MWh, not $2,000

`Integrated Marketplace Protocols 119` §8.2.5, printed pp. 356–357. Plan §3 card **P5**
proposes `voll=2000.0` citing "FERC 831 offer cap". SPP's posted **Safety-Net Energy Offer
Cap is $1,000/MWh**. The $2,000 caps in §8.2.5 are the **Virtual Energy** and
**Import/Export Transaction** caps — neither is a dispatchable resource offer. $2,000 is Order
831's *hard* ceiling on cost-verified offers, not SPP's posted cap; p. 344 confirms the soft-cap
shape (offers above $1,000/MWh must follow the Mitigated Offer Development Guidelines). Card P5
is the owner's to rule; this is the measured input it should be ruled against.

Also transcribed: Reg-Up/Down $500/MW, Contingency Reserve $100/MW, Uncertainty Reserve
$1,000/MW, Energy Offer Floor −$500/MWh, and the full 16-item list.

### VRL steps — and what they say about card P5

Exhibit 4-1, printed pp. 71–72: Resource Capacity **$100,000/MW** · Global Power Balance
**$50,000/MW** · Resource Ramp **$5,000/MW** · Operating Constraint (non-M2M) **$1,500/MW** at
*every* loading band >100 %…>104 % (the steps genuinely do not escalate) · **M2M Operating
Constraint = MISO's shadow price** per SPP-MISO JOA §3.1 · Spinning Reserve **$250/MW**.

This **supports** card P5's reasoning that SPP scarcity is VRL/reserve-shortage-driven rather
than a NEISO-style fuel overlay: the binding ceiling in an SPP shortage is the $250/MW spinning
VRL and the $50,000/MW power-balance VRL. The M2M row is also a real cross-seam coupling — SPP's
congestion ceiling on M2M flowgates *is MISO's shadow price* — which any SPP congestion work has
to respect.
