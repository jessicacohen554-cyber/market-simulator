## 2. The two new configs (rows 1–3), and why they carry no number

`configs/scenarios/spp_scenario_base_2026_2030.yaml` and `…_2026_2050.yaml`, cloned in form from the
six that shipped. The six are **byte-identical to each other modulo the ISO token** — verified both
ways (`diff <(sed s/CAISO/XXX/) <(sed s/NEISO/XXX/)` on both horizons, empty) — and the SPP pair is
byte-identical to CAISO's modulo the same token, verified the same way.

Each file sets exactly **four** keys, which is the whole point of a REF base (plan §3.0, quoted in the
files' own header): `mode: forecast`, `iso: SPP`, `start_year: 2026`, `end_year: 2030` / `2050`.
**There is no fifth key, so there is no SPP-specific value to cite and no tuned number to declare** —
every policy and driver axis is left at its `ScenarioConfig` default, which is exactly what row 2's
test (`test_base_varies_nothing_but_iso_and_horizon`) enforces field-by-field over every dataclass
field. Rules 5 `[R-NO-MAGIC]`, 21 `[R-DOF]` and 24 `[R-REGISTRY]`: nothing is introduced that any of
them governs. Rule 25 `[R-ISO-SCOPE]`: no other ISO's fitted value is carried in, because no value is
carried in at all.

These files do **not** authorize or schedule an SPP campaign solve. They are the config surface three
tests read; the campaign itself is the forecast program's, routed to W6 (plan §1 row 6).

## 4. Rule 22 in detail — the registration-marker gate (row 7)

The charter's STOP clause: *"if `test_registration_marker_gate` fails because an SPP run is registered
without a `complete` marker, that is the test being RIGHT about rule 22 — report what it asserts and
STOP on that one; never weaken a holdout gate."* **The clause does not fire, on three independent
grounds, each verified rather than assumed:**

1. **The gate itself passes.** The loop's load-bearing assertion is
   `hp.registration_refusals(years, iso, marker, freeze) == []`, evaluated per sidecar. It returns
   `[]` for **all seven** committed out-of-window sidecars. The failing line is the one after it: a
   hand-kept set of ISO names.
2. **The extra ISO is NYISO, not SPP** — and NYISO **holds** `complete`
   (`frontend/data/backcast/calibration-complete.json`, `complete.NYISO`, fourth grant, 2026-09-06),
   so the assertion's own message ("every registered holdout run must belong to a `complete` ISO")
   remains **true** after the extension. Nothing is relaxed; a stale list is corrected in the open.
3. **SPP has no holdout registration at all.** Enumerated at HEAD, the seven out-of-window sidecars
   are NEISO ×2, NYISO ×2, ERCOT ×2, PJM ×1. Every SPP registry sidecar declares years drawn from
   {2023, 2024, 2025} only, so no SPP run reaches this loop. SPP holds no marker of either tier, and
   the added comment says in place that **SPP must not be added to this list on sight** — an SPP
   holdout registration is a rule-22 breach this tripwire has to catch.

The allowlist is deliberately **hand-kept and not derived** from the marker file: deriving it from the
same JSON `registration_refusals` already reads would make it self-fulfilling and it would then test
nothing. It goes stale by design, which is what happened. The `>= 4` count tripwire, the
`tier_for_year == TIER_VALIDATION` assertion ("no locked-test year has ever been registered"), and the
per-sidecar refusal check are all unchanged. **No holdout gate, freeze, marker, tier map or sidecar
was touched by this lane.**
