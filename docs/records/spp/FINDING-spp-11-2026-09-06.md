### 3.4 Producer changes, and a defect they fixed

`scripts/data/fetch_eia930_subba_demand.py`, all additive. The MISO path is
unchanged: re-running `--iso MISO --years 2019` after every edit reproduces
`miso_subba_demand_2019.csv` **byte-identically** (`cmp` clean, both before
and after the span fix).

* `SUBBA_NAMES["SPP"]` — the 17 rows above.
* `PARENT_BA` — the Grid Monitor BA code per ISO. `SWPP ≠ SPP`, and the code
  is both the row filter and the `parent` column's value. MISO's ISO name and
  BA code coincide, which is why the old code could use `iso` for both.
* `_code()` — zero-pad only **numeric** sub-BA ids. MISO's are numeric
  (`"1"` → `"0001"`); SWPP's are alphabetic utility mnemonics (`WR`, `EDE`,
  `CSWS`) that the old unconditional `.zfill(4)` would have corrupted into
  codes EIA never publishes (`"00WR"`).
* `--combine` — write one `<iso>_subba_demand_<first>-<last>.csv`, the shape
  `miso_subba_demand_2023-2025.csv` already uses for the calibration window.

**The defect.** On the first (pre-fix) combined pull the file had **14
interior missing hours**: `2024-01-01T00..06` and `2025-01-01T00..06`. Cause:
SWPP is UTC−6, so the first seven UTC hour-ending stamps of each January are
published in the *previous* year's `Jul_Dec` extract, and the per-year period
filter dropped them as belonging to the neighbouring partition. That is
correct for a per-year file and **wrong** for a combined one, where those
hours are inside the file's own span. Under `--combine` the filter now widens
to the whole requested span. Measured: **14 gaps before, 0 after**, and the
row count lands on exactly 17 × 26,297.

The file still starts at `T07` rather than `T00`: the first seven hours of
2023 come from the **2022** `Jul_Dec` extract, outside the requested span.
That is a span boundary, not a hole, and it closes by itself whenever the
2019–2022 back years are intaken.

Blob-verified per rule 27 (the file is 308 lines): remote and local blob sha
`b4fa27cf872c0bbb88c4e0bba4fbc7081636e6dc`, 308 lines on both sides.

### 4.2 What this says for cards P2 and P3

Evidence only; the desk decides.

* **P2 (MISO seam).** `MISO` is far and away the largest and most volatile
  seam — the widest p5–p95 band of any DIBA by a factor of ~2 (−1,455 to +670
  MW in 2024), the only one that reaches multi-GW in both directions, and the
  only one whose *direction* is genuinely two-sided (export in 35–47 % of
  hours, i.e. it flips constantly rather than sitting on one side). Its
  annual net is small (−0.8 to −2.4 TWh) precisely because it flips. A scalar
  served schedule reproduces the net; it cannot reproduce the flipping, which
  is what a priced seam would. Both halves of the plan's P2 recommendation are
  visible here.
* **P3 (ERCOT DC ties).** `ERCO` clips at **+835 MW** in all three years —
  visible in the `max` column as an exact, repeated ceiling — consistent with
  the plan's 820 MW rating from the two DC ties (`ERCOT_DC_TIE_ZONE_MAP["SWPP"]`,
  Monticello 600 + Oklaunion 220 = 820 MW). The tie is used: 61–65 % of hours
  export, p95 +339 to +823 MW, net +0.5 to +1.2 TWh/yr. It is a real,
  frequently-loaded, hard-limited seam — but ~1.5 % of SWPP peak, which is
  the plan's own reason for a neighbour rather than an import node.
* `AECI` (Associated Electric, the Missouri co-op island inside SPP's
  footprint) is the largest *net* seam at +2.0 to +2.6 TWh/yr and is
  overwhelmingly one-directional (72–81 % export hours) — a candidate for a
  served schedule with no priced behaviour at all.
* `PNM` goes to **identically zero** from 2025 onward, and `SIKE` (Sikeston,
  MO) **first appears 2025-06-01**. SPP's DIBA set is not constant across the
  window; anything that hard-codes eleven seams for all three years is wrong.
