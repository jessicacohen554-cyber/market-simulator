Evolution & Policy

Results & Calibration

How the model's outputs are structured and validated. From Parquet caching and result export through forecast vs. backcast distinction to the calibration diagnostics that validate the model against real-world data.

①

Result Structure

When the LP solves, it produces a DispatchResult object containing the primal solution (generator dispatch, renewable production, storage charge/discharge, transmission flows) and dual solution (nodal prices). This result flows through several stages before landing on the dashboard.

Each stage is deterministic and reproducible — no intermediate files are committed, and the entire pipeline can be re-run from the cache.

Figure V26: Result data flow from LP solve to dashboard. Each stage is deterministic; only Parquet files are persisted. The dashboard ingests the JSON export to display results and historical runs.

The key insight: the Parquet file is the single source of truth. Everything downstream — emissions, plant-by-plant financials, annual summaries — is derived from it in a single pass. This means:

  • Reproducibility: Given a Parquet file and the configuration that produced it, all derivatives are deterministic.
  • Compact storage: The Parquet file is ~100–200 MB per ISO-year. Derivatives are computed on-the-fly at analysis time.
  • No intermediate commits: Results don't clutter the repository. Only the Parquet file needs to be kept if we want to re-derive outputs later.
②

What Gets Cached

Before solving a year, the runner checks if a Parquet file already exists for that scenario-year combination. The check uses a deterministic cache key derived from the scenario configuration (data sources, policy settings, solver parameters, etc.). If a cache hit occurs, the LP is skipped entirely and the cached result is loaded.

The cache directory structure mirrors the scenario registry:

bash
results/{iso}/{cache_key}/
├── year_2026.parquet          # Hourly dispatch + prices (8760 × n_vars)
├── year_2026_p1.parquet       # P1 result (before optional commitment screen)
├── year_2027.parquet
├── ...
├── year_2050.parquet
└── config.yaml                # Full scenario config (written once)

Each Parquet file contains:

  • dispatch — per-generator hourly output (MWh)
  • wind, solar — per-zone renewable production (MWh)
  • price — system and zonal LMP ($/MWh)
  • slack, dump — unserved demand and curtailed renewables
  • storage_charge, storage_discharge, storage_soc — battery dispatch and state-of-charge
  • flows — transmission line flows (MWh)
  • emissions — hourly CO₂, NOx by zone (optional)

Metadata in the file's schema includes the fleet context: unit IDs, heat rates, emission rates, zone assignments, and capacity totals. This lets any downstream tool reconstruct per-plant financials and emissions without re-deriving the fleet.

③

Forecast vs. Backcast

The model runs in two modes, set explicitly by ScenarioConfig.mode: forecast (projection) and backcast (historical validation). The mode is never inferred — it must be specified. The two modes differ fundamentally in their data inputs.

Forecast Mode (2026–2050)

  • Outages: Statistical availability by fuel type; parametric forced-outage rates (NERC, EIA-860)
  • Fuel prices: AEO-sourced forecasts (EIA); Henry Hub gas curves, coal regional index, renewable curtailment costs
  • Renewable CFs: Historical-average (eia-930 era-average by month, zone)
  • Weather year: Representative/synthetic (30-year median wind/solar profiles)
  • Fleet: EIA-860 known pipeline (construction-committed capacity additions)
  • Transmission: Base topology; no network upgrades unless explicitly added to config
  • No measured overlays: Pure forward-looking dispatch

Backcast Mode (2023–2025)

  • Outages: CAMPD unit-level outage windows (actual forced and scheduled outages by hour, 2023–2025)
  • Fuel prices: EIA-923 delivered fuel prices (actual coal, gas, oil prices by state-month); real Henry Hub for gas
  • Renewable CFs: EIA-930 measured grid-level generation by fuel (hourly, 2023–2025)
  • Weather year: Actual meteorological year (2023, 2024, or 2025); fixes the solar/wind resource to what actually happened
  • Fleet: Historical fleet composition (EIA-860 reference data for each year)
  • Transmission: Base topology (same as forecast)
  • Measured inputs only: No tuning or fitted parameters. Inputs are reproducible physical/market facts.
⚠️ Measured data is allowed only as a reproducible physical/market input, never as the answer. You can use CAMPD outage windows, actual fuel prices, and metered renewable output because these are grounded in physics or market design and could be regenerated for a forward year. What is forbidden: pinning a unit's dispatch to its observed generation, adding an offset tuned to the price residual, or rescaling an input to force the backcast to match. Those moves make the "fit" measure plumbing, not model skill. If a measured input makes the backcast worse, keep it and find the real root cause in the model. (See CLAUDE.md rule #13.)

Why two modes? Forecast mode answers "what if?"; backcast mode answers "how well does the model reproduce what happened?" Backcasts validate that the model's mechanisms — price formation, commitment, congestion, scarcity — mirror the real market. Only after validation do we trust the forecast.

A run is labeled a keeper when the C1–C8 determination rubric grades it structurally sound and it is the most structurally faithful run for its ISO — not the lowest-error one (the project's structural-fidelity-first rule). Keepers set the baseline for forward scenarios; probes are diagnostic tools that inform next-run tuning but do not enter the forecast production line. The rubric itself is detailed in § Calibration Diagnostics below.

④

Calibration Diagnostics

A backcast run is graded by the v2.x determination rubric (currently RUBRIC_VERSION 2.4) — a tiered, two-band rubric, not one flat tolerance band applied metric-by-metric. Its most important structural fact is a division of labour across two scripts: the diagnostic MEASURES, the verdict GATES.

  • legitimacy_diagnostics.py computes the D‑1…D‑10 legitimacy diagnostics — the diurnal-shape rows, the per-class forced-share summary, the driver windows — into the committed bundle artifact legitimacy_diagnostics.json.
  • calibration_verdict.py scores the twelve C1–C8 criterion-years, applies the tiers, tolerances, and caveat budgets, and emits one determination. It is stdlib-only, reads committed artifacts only, and never re-solves the LP — the committed run payload is the model side of every score.

The determination is one of three values, in decreasing order of confidence:

CALIBRATED Zero caveats of any kind, nothing skipped, no data-blocked target years.
CALIBRATED-WITH-CAVEATS In-band overall, but with enumerated caveats and/or unscored criteria — each one named in the reasons.
NOT-YET Any FAIL on any tier, or the C6 governance gate not passed, or a caveat budget exceeded.

The eight criteria, three tiers

Twelve scored criterion ids are grouped as C1–C8, each carrying a tier. The tier sets a criterion's tolerance philosophy, not an escape hatch: a FAIL on any tier forces NOT-YET.

  • Load-bearing  C1 fuel-mix by class, C2 gas/coal system volume, C3a mean LMP, C3b monthly price shape, C5a CO₂ vs eGRID. These certify the intended uses directly; two-band where a published commercial comparable exists.
  • Supporting  C3c scarcity tail, C4 fleet hourly dispatch correlation, C5b/C5c storage throughput & shape. Sub-annual dynamics, scored against a single wide band.
  • Protective  C6 governance gate, C7 diurnal shape (D‑1), C8 forced-energy share (D‑2). The anti-self-deception gates — C6 is never caveatable.

Two bands and the caveat budget

Load-bearing criteria with a published commercial comparable are scored against two bands: a tight target band (a clean PASS) and a wider commercial band (what a commercial forecaster would accept). Landing between them yields an auto commercial-band caveat — unbudgeted, because it sits inside the certification claim by construction. A FAIL becomes a budgeted MEASURED_LIMIT caveat only where an explicit ledger entry documents the actual as the limitation.

Budgets are small and asymmetric: ≤ 1 protective ledgered caveat (C6 itself is never caveatable) and ≤ 3 non-protective ledgered caveats. Exceed either — or leave any criterion unscored, or fail C6 — and the run drops to NOT-YET. An unscored criterion is never a silent pass: it caps the determination at CALIBRATED-WITH-CAVEATS and is named in the reasons.

Note — C3a/C3b are single-band in effect. Since v2.3 the price target bands coincide with the commercial bands (±10% on the load-weighted mean LMP, 0.20 monthly NRMSE), so there is no live commercial-band caveat range on the two price criteria: inside the band is a clean PASS, outside is a FAIL (ledgerable only as a measured-input limitation). Don't read a price-caveat range into the rubric that no longer exists.

The forced-energy budget (C8)

Floors are commitment scaffolding, not the dispatch model — so C8 caps the share of a class's energy that may clear at binding floors: < 15% for peakers, < 30% for merchant classes, gated only for classes ≥ 2% of ISO load (smaller classes are reported by the diagnostics but never gated).

A material class above its cap is not an automatic FAIL. It escalates to a grounded-above-budget conditional pass requiring both: (a) provenance — every binding non-exempt mechanism clears its D‑4 driver window (a mechanism with no declared window fails by definition), and (b) shape — the class clears its D‑1 diurnal profile gates. Both clear → a clean PASS surfaced as a report note (the high forcing stays visible and auditable, counting against no budget); either fails → FAIL, the "forcing variables are wrong" signal.

Determination ≠ keeper. The determination is machine-scored; the keeper decision is the human judgment layered on top. A keeper is the most structurally faithful run for its ISO — never the lowest-error one. A more-accurate run that is missing real market structure is not a keeper (CLAUDE.md rule 1). The moment a run is marked keeper, its bundle and metadata are registered on the calibration dashboard and committed to the repository.

⑤

Ablation Twins & the DOF Ledger

The rubric proves a run matches the market. Two further keeper obligations prove the match wasn't bought — that the model earns its fit with real mechanisms, not free parameters tuned to the residual. Both are required of every keeper under CLAUDE.md rule 21 ("Every keeper carries a DOF ledger and an ablation twin")1: the zero-forcing ablation twin quantifies what the floors do, and the DOF ledger enumerates every free parameter and how it was identified.

The zero-forcing ablation twin

An ablation twin is a re-solve of a keeper's exact config with every merchant floor, bridge, drag, and availability-haircut turned off — keeping only the structural must-run set (nuclear must-run, CHP steam-following, coal take-or-pay) and the firm-import boundary. It is produced by the config transform ScenarioConfig.as_zero_forcing_ablation(cfg), applied after all per-ISO defaults and overrides so that config-level defaults (e.g. CAISO's net-load drag or RA must-offer) are forced off regardless of how they were set.

Crucially, the off-list is derived, not hand-maintained: it is the union of every entry in the D‑2 mechanism registry (floor_mechanisms.zero_forcing_field_overrides()) plus the WEFOR availability haircuts. A companion assertion, assert_ablation_coverage(), raises if any mechanism id is neither explicitly KEPT nor ablated — so a newly added merchant floor is ablated by default and cannot silently escape the twin.

The keeper-vs-twin per-class energy delta is what each floor buys. A delta explainable only as "the floor buys the residual" is an open root-cause item, not a calibrated parameter (rule 1). In the illustrative twin below, the structural classes (nuclear, coal take-or-pay) barely move; the merchant-floored classes (steam gas, CT peakers) carry real floor-bought energy; and the flexible margin (gas-CC) absorbs the offset with a negative delta — floors mostly reallocate energy between classes rather than add it.

The DOF ledger

The degrees-of-freedom (DOF) ledger is the free_parameters block written into a bundle's calibration_attestation.json (schema dof-ledger/v1): an explicit enumeration of every free parameter the run depends on, each with an entry of the form { name, where, identification, lineage_solves, value?, source?, root_cause? }, built by scripts/build_dof_ledger.py. The load-bearing field is identification — how the parameter's value was pinned down:

published — a published market/physical quantity measured-physical — a frozen derive script over measured data (rule 23) residual — moved a backcast residual (only inside the rule 1 offer-curve scope)

The discipline lives on the last class: a residual entry must carry a non-empty root_cause — the builder raises a ValueError otherwise. A residual that can only be closed by a tuned value is an open root-cause issue, not a parameter. The ledger makes every such open issue visible and countable rather than buried in an input.

Enforcement — audit_keepers E8 & E9

Neither obligation is honour-system: both are checked by scripts/audit_keepers.py, which the CI quarantine-gates job runs on every registered bundle.

  • E8 (DOF ledger) — FAILs a keeper whose attestation has no free_parameters section, or that has a residual entry lacking a root cause. Unconditional; every keeper carried a ledger when it landed.
  • E9 (ablation twin) — FAILs a keeper without a resolvable ablation_twin sidecar link; a declared-but-broken link FAILs regardless of any grace. The rollout grandfather list was designed to self-empty as keepers were re-registered with twins, and today all current keepers carry registered twins.

1.  A note on rule numbering. The code comments for both features cite "CLAUDE.md rule 20", but the obligation is rule 21 in the current CLAUDE.md ("Every keeper carries a DOF ledger and an ablation twin"; rule 20 there is a different rule, "Forced energy is budgeted"). The gap is a documented renumbering offset, not a contradiction: the protective rules were numbered 16–25 in the legitimacy audit's §8, then CLAUDE.md later inserted rule 16 (all-years-one-bundle), shifting them to 17–26 — so audit rule 20 = CLAUDE.md rule 21. Both labels point at the same obligation; the code comments simply predate the shift and should not be "fixed" against it. ↩

The Calibration Dashboard

Every backcast run — keeper or rejected probe — is registered on the deployable backcast results dashboard the same session it completes. The dashboard is a static HTML site that displays the calibration results, keeper timelines, and per-run metadata across all ISOs and years.

Results do not live in chat; they live on the dashboard. A run is not "done" until its Parquet bundle and metadata files are committed and pushed to the repository. The workflow is:

  1. Solver finishes. A Parquet file lands in results/{iso}/{cache_key}/.
  2. Run is scored. The C1–C8 determination rubric scores the committed artifacts (see § Calibration Diagnostics) and emits one determination — legitimacy_diagnostics.py writes the D-rows, calibration_verdict.py reads and gates them.
  3. Dashboard registration. Use the calibration-report skill (or run scripts/dashboard_add_run.py) to commit the run's metadata to frontend/data/backcast/registry/{run_id}.json and the run script to runs/{run_id}.js.
  4. Push to origin. The Parquet bundle, sidecar, and run manifest are committed. The GitHub Pages deploy auto-builds the dashboard HTML from the manifest.

Keeper vs. probe: A keeper grades in-band under the rubric and is judged the most structurally faithful run for its ISO (never the lowest-error one). It becomes the baseline for the next forecast year. A probe is a diagnostic run isolating a single-year effect or tuning option; it is never used in production and is pruned from the dashboard after its insights are extracted.

The top 15 runs per ISO are retained; older runs are pruned to keep the dashboard lean. Retention order is by status (keepers first) and recency.

The dashboard is the source of truth for calibration status. When reviewing a run, always check the dashboard entry for the keeper decision, action items, and confidence level. The prose notes in the dashboard (linked from each run's metadata) explain the root causes of any caveats or failures and suggest the next tuning step.
