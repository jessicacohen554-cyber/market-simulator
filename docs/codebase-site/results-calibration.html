Evolution & Policy

Results & Calibration

How the model's outputs are structured and validated. From Parquet caching and result export through forecast vs. backcast distinction to the calibration diagnostics that validate the model against real-world data.

①

Result Structure

When the LP solves, it produces a DispatchResult object containing the primal solution (generator dispatch, renewable production, storage charge/discharge, transmission flows) and dual solution (nodal prices). This result flows through several stages before landing on the dashboard.

Each stage is deterministic and reproducible — no intermediate files are committed, and the entire pipeline can be re-run from the cache.

Figure V26: Result data flow from LP solve to dashboard. Each stage is deterministic; only Parquet files are persisted. The dashboard ingests the JSON export to display results and historical runs.

The key insight: the Parquet file is the single source of truth. Everything downstream — emissions, plant-by-plant financials, annual summaries — is derived from it in a single pass. This means:

  • Reproducibility: Given a Parquet file and the configuration that produced it, all derivatives are deterministic.
  • Compact storage: The Parquet file is ~100–200 MB per ISO-year. Derivatives are computed on-the-fly at analysis time.
  • No intermediate commits: Results don't clutter the repository. Only the Parquet file needs to be kept if we want to re-derive outputs later.
②

What Gets Cached

Before solving a year, the runner checks if a Parquet file already exists for that scenario-year combination. The check uses a deterministic cache key derived from the scenario configuration (data sources, policy settings, solver parameters, etc.). If a cache hit occurs, the LP is skipped entirely and the cached result is loaded.

The cache directory structure mirrors the scenario registry:

bash
results/{iso}/{cache_key}/
├── year_2026.parquet          # Hourly dispatch + prices (8760 × n_vars)
├── year_2026_p1.parquet       # P1 result (before optional commitment screen)
├── year_2027.parquet
├── ...
├── year_2050.parquet
└── config.yaml                # Full scenario config (written once)

Each Parquet file contains:

  • dispatch — per-generator hourly output (MWh)
  • wind, solar — per-zone renewable production (MWh)
  • price — system and zonal LMP ($/MWh)
  • slack, dump — unserved demand and curtailed renewables
  • storage_charge, storage_discharge, storage_soc — battery dispatch and state-of-charge
  • flows — transmission line flows (MWh)
  • emissions — hourly CO₂, NOx by zone (optional)

Metadata in the file's schema includes the fleet context: unit IDs, heat rates, emission rates, zone assignments, and capacity totals. This lets any downstream tool reconstruct per-plant financials and emissions without re-deriving the fleet.

③

Forecast vs. Backcast

The model runs in two modes, set explicitly by ScenarioConfig.mode: forecast (projection) and backcast (historical validation). The mode is never inferred — it must be specified. The two modes differ fundamentally in their data inputs.

Forecast Mode (2026–2050)

  • Outages: Statistical availability by fuel type; parametric forced-outage rates (NERC, EIA-860)
  • Fuel prices: AEO-sourced forecasts (EIA); Henry Hub gas curves, coal regional index, renewable curtailment costs
  • Renewable CFs: Historical-average (eia-930 era-average by month, zone)
  • Weather year: Representative/synthetic (30-year median wind/solar profiles)
  • Fleet: EIA-860 known pipeline (construction-committed capacity additions)
  • Transmission: Base topology; no network upgrades unless explicitly added to config
  • No measured overlays: Pure forward-looking dispatch

Backcast Mode (2023–2025)

  • Outages: CAMPD unit-level outage windows (actual forced and scheduled outages by hour, 2023–2025)
  • Fuel prices: EIA-923 delivered fuel prices (actual coal, gas, oil prices by state-month); real Henry Hub for gas
  • Renewable CFs: EIA-930 measured grid-level generation by fuel (hourly, 2023–2025)
  • Weather year: Actual meteorological year (2023, 2024, or 2025); fixes the solar/wind resource to what actually happened
  • Fleet: Historical fleet composition (EIA-860 reference data for each year)
  • Transmission: Base topology (same as forecast)
  • Measured inputs only: No tuning or fitted parameters. Inputs are reproducible physical/market facts.
⚠️ Measured data is allowed only as a reproducible physical/market input, never as the answer. You can use CAMPD outage windows, actual fuel prices, and metered renewable output because these are grounded in physics or market design and could be regenerated for a forward year. What is forbidden: pinning a unit's dispatch to its observed generation, adding an offset tuned to the price residual, or rescaling an input to force the backcast to match. Those moves make the "fit" measure plumbing, not model skill. If a measured input makes the backcast worse, keep it and find the real root cause in the model. (See CLAUDE.md rule #12.)

Why two modes? Forecast mode answers "what if?"; backcast mode answers "how well does the model reproduce what happened?" Backcasts validate that the model's mechanisms — price formation, commitment, congestion, scarcity — mirror the real market. Only after validation do we trust the forecast.

A run is labeled a keeper if it passes calibration checks (generation mix, price duration curve, average price, and capacity factors, each within ±5% of measured). Keepers set the baseline for forward scenarios; probes are diagnostic tools that inform next-run tuning but do not enter the forecast production line.

④

Calibration Diagnostics

Every backcast run is validated against four ordered diagnostics (check_generation_mix, check_price_duration_curve, average price, check_cf_band_occupancy). Failure in check #1 usually explains failures in #2–#4, so they're designed to be interpreted top-down. Each metric is graded against a single DEFAULT_TOLERANCE of ±5%, and every comparison is a binary pass / fail (a metric with no benchmark supplied is reported skipped) — there is no intermediate "warning" tier. A CalibrationReport passes only when no diagnostic fails.

Interpretation: This example keeper run passes 13 of 14 metrics (93%) within the ±5% band; the single failure is the P10 price overshoot (+20.5%). The near-misses that sit just inside tolerance (gas-CT and solar generation, coal CF) and that one failure all trace to the same root cause: the coal must-run tranche offer curve is priced too low, forcing the model to run coal plants beyond their actual dispatch. The fix is structural (adjust the coal sigmoid steepness parameter in the next run), not a tuning tweak.

Note the distinction: CalibrationReport.passed is strict — it is true only when no diagnostic fails. The keeper decision is a separate, human judgment that can certify a structurally-sound run even with a failing diagnostic, provided the failure is traceable to a tunable parameter rather than a missing mechanism (per the project's structural-fidelity-first rule). The moment a run is marked keeper, its bundle and metadata are registered on the calibration dashboard and committed to the repository.

⑤

The Calibration Dashboard

Every backcast run — keeper or rejected probe — is registered on the deployable backcast results dashboard the same session it completes. The dashboard is a static HTML site that displays the calibration results, keeper timelines, and per-run metadata across all ISOs and years.

Results do not live in chat; they live on the dashboard. A run is not "done" until its Parquet bundle and metadata files are committed and pushed to the repository. The workflow is:

  1. Solver finishes. A Parquet file lands in results/{iso}/{cache_key}/.
  2. Calibration checks run. The four diagnostics are computed; a CalibrationReport is generated.
  3. Dashboard registration. Use the calibration-report skill (or run scripts/dashboard_add_run.py) to commit the run's metadata to frontend/data/backcast/registry/{run_id}.json and the run script to runs/{run_id}.js.
  4. Push to origin. The Parquet bundle, sidecar, and run manifest are committed. The GitHub Pages deploy auto-builds the dashboard HTML from the manifest.

Keeper vs. probe: A keeper is a run passing calibration checks and deemed structurally sound. It becomes the baseline for the next forecast year. A probe is a diagnostic run isolating a single-year effect or tuning option; it is never used in production and is pruned from the dashboard after its insights are extracted.

The top 15 runs per ISO are retained; older runs are pruned to keep the dashboard lean. Retention order is by status (keepers first) and recency.

The dashboard is the source of truth for calibration status. When reviewing a run, always check the dashboard entry for the keeper decision, action items, and confidence level. The prose notes in the dashboard (linked from each run's metadata) explain the root causes of any warnings or failures and suggest the next tuning step.

🎯 Key takeaway: Results flow deterministically from LP solve → Parquet cache → derived outputs → JSON export → dashboard. The cache is the gate; the dashboard is the publication. Backcast validation isolates structural issues from tuning tweaks. Every keeper run becomes the calibration baseline; probes are temporary diagnostic tools.
