The Engine

Solving & Pricing

Three LP solves per year reconcile startup economics with clearing prices. The dual on every energy-balance constraint is the zonal price — no separate pricing model needed.

①
Motivation

Why Three Solves?

A single LP pass is enough to clear energy — but it can't price it right. The core problem is startup costs. Gas turbines cost $50k–$200k to start, and that cost must be recovered in the hours the unit runs. If a generator bids its startup cost directly, it may set the clearing price, but the dispatch becomes inconsistent: the unit needs to know its run length to amortise the cost, but the run length depends on the price it sets.

Three passes break this circularity cleanly — and stay pure LP, avoiding the MIP complexity of true unit commitment:

Pass Cost vector Purpose Output
P0 Base MC (fuel + VOM + carbon) Dispatch at true variable cost — reveals how long each unit runs per month Run-length distribution per unit per month
P1 Bid MC = base MC + amortised startup markup μ Sets clearing prices. Markup reflects real startup economics in the LMP LMP duals, P1 dispatch, warm basis for P2
P2 Bid MC on a commitment-screened fleet Optional: decommit unprofitable CC/CT runs below IRR hurdle (off by default) Commitment decisions; P2 re-dispatch if enabled

Prices = LP duals on the energy-balance constraints.

No post-solve pricing model, no uplift calculation, no separate price formation step. When P1 solves, each zone's energy-balance constraint shadow price is the zonal LMP.

Coal & nuclear: no markup

compute_monthly_markup() sets μ = 0 for coal, nuclear, and non-thermal units. Coal's take-or-pay structure makes startup economics moot; nuclear runs continuously by design.

P2 adequacy backstop

The commitment screen never creates unserved demand. If decommitting a unit would leave committed capacity below P1's thermal dispatch in any zone-hour, apply_commitment_with_coal_pin() restores the cheapest decommitted units until the floor is met.

③
Mechanism

How Startup Costs Enter Prices

Between P0 and P1, compute_monthly_markup() (commitment.py:173) turns a unit's raw startup cost into a per-MWh price adder. The calculation is simple but consequential:

μ  =  startup_cost  ÷  avg_run_length
μ — the per-MWh startup markup added to base MC in P1.
startup_cost — fixed cost to start the unit ($), fuel-type specific.
avg_run_length — mean hours per run in each calendar month, measured from P0 dispatch (threshold: unit output > 5% of Pmax).

Short runs → high markup per MWh (startup cost spread over few hours). Long runs → low markup (cost well-amortised). This makes the bid-cost curve endogenous: units that tend to run briefly (peaking CT) carry larger markups than baseload CC units that run weeks at a stretch.

Monthly granularity matters

Run lengths are measured per calendar month (seasonal for gas_st). A CC unit may run 300 h/start in winter (baseload) but only 6 h/start in mild spring. Monthly markup captures this seasonal variation in clearing prices — winter CC prices are barely affected; spring prices carry a larger per-MWh startup adder.

How prices become outputs

After P1 solves, HiGHS returns dual variables on every constraint row. The dual on zone z's energy-balance row at hour t is LMP[z,t]. No further computation needed — the LP solver has already computed the marginal value of one more MWh at that zone and hour. These duals are stored in DispatchResult.prices and written to the per-scenario-year Parquet cache.

⑤
Performance

Warm-Start & Solve Performance

The three-solve structure pays for itself through basis reuse. Each pass warm-starts from the previous one's optimal basis — the set of active constraints HiGHS identified. Because P0 and P1 share the same constraint structure (only the objective changes), P1 typically reaches optimality in a handful of dual-simplex pivots rather than a full solve.

~5× warm-start speedup (P1 from P0)
P0 solves the full ~200k-variable LP from scratch (~8–15 min on a large ISO). P1 re-enters at the P0 basis and re-optimises in minutes. The HiGHS set_hot_start() call passes the primal and dual solutions.
Sequential years, parallel ISOs
Years within a single run must be sequential — each year's LP uses several GB of RAM and the capacity-evolution state is threaded forward. But separate ISO invocations (e.g. CAISO and PJM) have no dependency and are launched as concurrent background jobs.
Check-before-run caching
Before any solve, cache.py checks whether the Parquet output already exists for this scenario + year hash. Re-running the same config is instant — the result is loaded from disk, not recomputed. P1 and P2 are cached separately.
HiGHS direct CSC interface
The LP is assembled as a CSC sparse matrix (scipy.sparse) and passed directly to highspy. No modelling-layer overhead (Pyomo, PuLP, or scipy.optimize are forbidden by project rules). Kronecker tiling builds the full 8760-hour constraint matrix without Python loops.

Full 8,760 hours — always

The LP always solves the full year. No representative days, no time-slice reduction. This is a non-negotiable project rule: representative days create systematic bias in storage dispatch, ramping costs, and seasonal price formation that no weighting scheme fully corrects.
